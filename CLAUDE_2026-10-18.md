## Grain change (the core decision)

V1 used to store **one row per award** (lifetime total in `awd_amount`). V2 already
decided — and we adopted — **one row per award PER FISCAL YEAR**. A 5-year grant is now
5 rows, `awd_amount` is that year's own amount, not a lifetime total.

Scope: **FY2021–current only**, both NSF and NIH.

## Performance bug found and fixed (real, not hypothetical)

`get_field_wide_stats()` and `get_heatmap_data()` scan the full `awards` table grouped
by `nih_institute` or `dir_abbr`. SQLite's planner was picking a same-prefix index
(`idx_awards_source_fy_opp`, meant for CFDA/USASpending queries) over a proper covering
index, **even after `ANALYZE`** — confirmed this is a genuine planner quirk, not a data
or I/O problem (forcing the right index via `INDEXED BY` took it from **90s → 1.08s**
on NIH's 481K rows). NSF never showed this because its table (101K rows) is small enough
that the bad plan's cost was invisible. Fixed by adding two covering indexes
(`(source, nih_institute, fiscal_year)` and `(source, dir_abbr, fiscal_year)`) and
hinting them explicitly in the two query functions above. Verified in the browser:
NIH's Home page (Program Breakdown, heatmap, Sankey) now loads in a few seconds.

**Known gap:** only the two most-common drill-down cases (top-level NIH institute,
top-level NSF directorate) got covering indexes + hints. Deeper drill-downs
(`institute_filter` → `activity_code`, `dir_filter` → `div_abbr`/`pgm_ele_name`) weren't
checked — they're naturally narrower (an equality filter cuts the row count a lot) so
likely fine, but not verified the way the top-level views were.
